판단 상시 실행 윈도우 서버라는 요구사항엔 REST API가 더 적합 — 64bit 그대로 쓰고 영웅문 자동로그인 세션 불안정성에서 자유롭다. 다만 2025-06 출시로 사례·서드파티 라이브러리가 아직 얕고 Rate limit 실측치가 공식 수치와 어긋난다는 보고가 있어, PoC에서 REST API를 우선 검증하고 안정성 이슈가 발목을 잡으면 Open API+를 병행 검토하는 투트랙을 권장한다.

파이썬 연동: Open API+는 pykiwoom, breadum/kiwoom 등 32bit 래퍼가 다수. REST API는 공식 GitHub에 Python 3.13 클라이언트·OAuth/REST/WS 런타임·CLI(kwcli)가 제공되며 337개 API 스펙 + Postman Collection이 포함돼 있다.

자동매매 알고리즘

"상승 종목 매매" + "10% 하락 시 물타기" 요구사항에 대한 5개 알고리즘 궁합 비교.

알고리즘개요장점단점튜닝 파라미터
이동평균 크로스단기MA가 장기MA 상향 돌파추세장 강함, 구현 단순후행지표, 횡보장 저조MA 기간 (5/20, 20/60)
모멘텀 스크리닝상승률·거래량 급증 종목 발굴요구사항과 직접 일치추격매수 고점 리스크상승률/거래량 임계값
RSI 평균회귀30↓매수, 70↑매도박스권에서 유효강추세엔 역행 손실RSI 기간, 30/70 임계값
변동성 돌파전일 변동폭×K 돌파 시 매수단기 트레이딩 검증 사례多휩쏘(되돌림) 손실K값(통상 0.5), 관찰기간
분할매수(물타기)하락 시 추가매수로 평단 인하요구사항 자체와 일치하락 지속 시 손실 누적하락률, 1회 비중, 최대횟수
추천 조합 모멘텀 스크리닝 + 변동성 돌파를 진입 로직 메인 축으로, 물타기 규칙을 리스크 관리 계층으로 결합. 이동평균 크로스는 시장 국면 판별용 보조 필터로 병행. 단, 사용자 요구사항에 손절 조건이 없어 최대 추가매수 횟수·총 투입한도·최종 손절선은 반드시 별도 확인해야 무한 물타기를 막는다.

웹 조회 방식: React + 얇은 조회 API

React를 유지하므로 브라우저와 MySQL 사이에 최소한의 조회 API가 필요하다. 혼자 쓰는 도구라 최대한 얇게 둔다.

구조 서버모듈은 API를 거치지 않고 MySQL에 직접 기록한다. 웹은 React → 조회 전용 API → MySQL. 브라우저는 MySQL에 직접 접속할 수 없어 API 계층은 남기되, 쓰기 엔드포인트 없이 SELECT만 수행하는 얇은 서비스로 줄인다.
기준Java (Spring Boot)Python (FastAPI)
스택 통일서버모듈과 별도 스택서버모듈(Python)과 통일
1인 유지보수보일러플레이트 多간결, Swagger 자동문서화
React 연동REST로 문제없음REST로 문제없음 (동등)
워크로드 궁합CPU 바운드/대규모 강점I/O 바운드(DB 조회)에 강점
배포JVM, 상대적으로 무거움가볍고 컨테이너 친화적
추천 Python (FastAPI). 서버모듈과 언어가 통일되고, 하는 일이 DB 조회 + JSON 응답뿐이라 Java의 엔터프라이즈 이점이 필요 없다. 사용자 1명이라 인증·확장 설계도 최소로 충분하다.
확인 필요 원래 요구사항에 "API 모듈에도 UI가 있어야 한다"가 있었다. 1인 사용이면 FastAPI 내장 Swagger 화면(/docs)으로 API 점검이 가능한데, 이것으로 충분한지 별도 관리 화면이 필요한지 확인이 필요하다.
보안 API용 MySQL 계정은 SELECT 전용으로 분리하고, API는 localhost/내부망에만 바인딩한다. 외부에서 접속한다면 토큰 인증 또는 VPN이 필수 — 계좌·거래 정보가 노출되면 안 된다.

전체 아키텍처 방향

서버모듈 · DB · 조회 API · React 웹, 네 조각이 붙는 그림과 착수 순서.

서버모듈
Windows 상시실행 · Python + UI
키움 API 연동 · 알고리즘 엔진
→
MySQL
거래·체결·로그
알고리즘 파라미터 이력
←
조회 API
Python · FastAPI
SELECT 전용 계정 · 쓰기 없음
→
React 웹
거래 결과 검색/조회
결정됨 서버모듈은 API를 거치지 않고 MySQL에 직접 기록한다. 웹은 React가 조회 전용 API를 통해 같은 DB를 읽는다.

개발 착수 순서

  1. 키움 REST API 모의투자 계좌로 시세 조회/모의 주문 PoC — 인증, Rate limit 실측, WS 재연결 검증
  2. MySQL DB 스키마 설계 (시세 이력 · 포지션 · 주문/체결 로그 · 알고리즘 파라미터)
  3. 알고리즘 모듈 개발 및 모의투자 백테스트/포워드테스트
  4. 조회 API 개발 (FastAPI, SELECT 전용 DB 계정, 조회 엔드포인트만)
  5. React 웹 프런트 개발
  6. 모의투자 충분 검증 후 실계좌 소액 전환

리스크 / 주의사항

  • 실계좌 전환 전 모의투자 충분 기간 검증 필수
  • 조회 API는 SELECT 전용 DB 계정으로만 접속하고, 접속 범위 제한(localhost/VPN)과 인증이 필수
  • REST API는 2025-06 출시된 신규 서비스 — Rate limit 실측치가 상충하는 보고가 있어 보수적인 요청 큐잉/재시도 로직 필요
  • 24시간 상시 운영 시 세션/토큰 재발급 로직 필수 (OAuth 토큰은 만료 전 재발급 권장이라는 민간 자료 언급 — 공식 문서 재확인 필요)
  • 한국거래소가 2023년부터 "고빈도 알고리즘 거래" 사전등록을 의무화, 개인투자자도 적용 대상이라는 보도 확인 — 이 프로젝트의 매매 주기가 해당 기준에 걸리는지는 별도 확인 필요
  • 증권사 공통적으로 "자동 실행되더라도 투자 판단·실행 책임은 이용자 본인"이라 명시 — 별도 사전심의 절차 유무는 이번 조사로 확인되지 않아 키움증권 고객센터 문의 권장
